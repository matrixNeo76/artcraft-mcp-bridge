# Change log

## 2026-10-13
* **Fix**: the CI step "deterministic installer" counted a **fixed number of entries** (11) and the first push after PdfCraft moved to the [translator](tools/craft-bridge-ui.md) failed there: the installer produced 12. The task of a check is to notice a change, and a constant that must be updated by hand only notices it when someone remembers to update it. Now the expected entries are **asked of the shim table** (`--dump-apps`): every one of its 11 must be there, plus exactly one outside it, and that one must name the translator. Proved in both directions: with the entry missing → `entry fuori dallo shim: 0, attesa 1`, and with the translator gone from its command line → `l'entry fuori dallo shim non nomina il traduttore: pdfcraft`.
* **Change**: the **documentation is now in English** — every node of the OKF bundle (`docs/**`), plus `README.md` and `AGENTS.md` — so that it can be read by everyone; `README.md` is the main one and is translated into `README.it.md`, `README.es.md` and `README.zh.md`. Two nodes were renamed with it: `docs/reference/analisi.md` → [analysis.md](reference/analysis.md) and `docs/reference/piano.md` → [plan.md](reference/plan.md). The prose inside the code (comments, docstrings, CLI messages) is still Italian and is a separate, tracked change. The bundle stays conformant (`okfgen validate docs --strict`: 32 concepts, 0 errors) and every internal link was checked.
* **Added**: the **attach flag** is no longer something we remember: `craft-bridge-mcp.py --flags` asks **every CLI** for its own `--help` and compares it with what the table declares (`--connect` for seven apps, `--bridge` for four, none for PdfCraft). Three outcomes: confirmed, **not confirmed** (the table claims an option the help does not name — or the help names one the table does not use: the app changed, or the table is old), and unreadable (the CLI prints no help: the flag stays a declaration, and it is written down as one). The helps are requested in parallel: ~0.4 s for twelve, and the order of the results stays the table's.
* **Added**: `doctor` has the `flag di aggancio` check: `ok` when the CLI help confirms what the table uses (measured **12/12**: 11 attaches and 1 by translation), `FIX` with the action `--flags` when it does not confirm it, `nota` when the CLI is mute. The fault it prevents: an updated app that renames or removes the option, with the table promising something that no longer exists — and a fault one would only see at the first connection.
* **Added**: a place to inject the case, like `--config` and `--feed-dir`: `doctor --apps-file TABLE.json` (and `CONFIG.apps_table(source)`) let the diagnosis be exercised on a test table, without touching the installed apps. It is also how the suite demonstrates the `FIX`.
* **Measurement**: suite at **23 cases** (19 in `--static`), 23/23 and 19/19 with `--ci`, three of them new on the flag: the six verdicts of the comparison on fake CLIs, the `doctor` line in both directions, and the measurement on the real CLIs with the diagnosis repeating the same verdict. Cost: the whole suite goes to ~70 s and `--static` to ~32 s, because every `doctor` now talks to twelve CLIs; OKF bundle at 32 concepts and 161 relations.
* **Added**: `craft-bridge-ui.py`, the **translator of the PdfCraft window**. It is the only app whose MCP server has no bridge flag (`pdfcraft-cli mcp --connect` → `unknown option`), but its channel drives it perfectly: the window is therefore translated into MCP, **one method per invocation** (`pdfcraft-cli ui --control FILE <method>`). The 15 tools are the methods the app declares, not an invented list; the parameter values travel serialised as JSON, because the CLI re-reads them with the right type (a `true` string stays a string).
* **Added**: the two modes here too, declared as for the shim: a window that answers → the 15 methods of the window; window closed → delegation to the vendor's **headless** server, byte for byte; `--require-bridge` exits 3 instead of falling back. A fault of the app arrives as `isError` with its message, and if the window disappears mid-session the diagnosis is explicit.
* **Measurement**: window on port 48129 (pid 42336), `1440x920`, CLI `pdfcraft-cli 0.7.1` from the `App Paths` registry; `initialize` 0.23 s and 15 tools, `ui_state` 0.05 s, `ui_commands` **192 commands**, `ui_inspect` **107 widgets**, `ui_screenshot` 0.20 s → 197 KB PNG as image content ([reports/pdfcraft-finestra.png](../reports/pdfcraft-finestra.png)); `ui_click` on a non-existent label → `isError` with the CLI message; catalogue `15 metodi nostri, 15 dall'app: coincide`.
* **Added**: the `pdfcraft` entry now goes through the translator (the entries rewritten by the installer are **12**, not 11) and `doctor` has a tenth check, `finestra pdfcraft`: `ok` if the methods match the ones the app declares, `nota` if the window is closed (not a fault: the entry falls back), `FIX` if the translator does not answer at all. The installed copies watched are now **three**.
* **Fix**: the comparison with the published release looked at the shim table, so `pdfcraft` stayed outside a check that now concerned it, since the bridge serves it. The table used for the comparison is the one of the apps **served by the bridge** (`CONFIG.bridge_table()`, used by `feed` and `doctor`): 12 of 12 aligned, and the only feed entry outside the bridge remains `artcraft-launcher`.
* **Fix**: `craft-bridge-verify.py` read the mode only for the entries that name the shim, so the translator's stayed `modo=n/a` and an `--expect bridged` **did not concern it**: the verification was silent about an entry that could be in a mode other than the one demanded. Now the mode is read for the translator too — measured `pdfcraft modo=bridged tool=15`, and the same line becomes a KO with `--expect headless`.
* **Fix**: `craft-bridge-launch.py --list` printed the PdfCraft row **before** the table header (a section with no header); now it has its own, with its own columns (transport, mode).
* **Measurement**: suite at **20 cases** (16 in `--static`), 20/20 and 16/16 with `--ci`, including four cases on the translator: three **without apps** (a fake PdfCraft that authenticates with the file's token, answers like the app and is shut down mid-session; a fake headless server for the fallback) and one live that is **skipped with a reason** if the window is not there. Config entries verified with the real command: 13/13 OK, **12 with a bridge**. Tool inventory: **618** (PdfCraft goes from 161 to the window's 15 methods). OKF bundle: **32 concepts**, 156 relations (161 after the flag check above).
* **Added**: app and CLI paths are no longer written by hand: they are resolved by the `App Paths` registry, the entry every app's MSI installer writes and that Windows uses to open it by name. The table stays as a confirmation and as a fallback; `--dump-apps` carries `cli_source`, `declared_cli`, `app_exe` and `app_hive`, and `craft-bridge-launch.py --list` shows the `percorso` column, so a divergence is visible instead of ageing away in silence.
* **Fix**: the reading looks at **both hives**, user before machine. The first version read only `HKLM`: that is fine on this machine (the 12 packages are per machine), but the launcher itself is installed per user and registers in `HKCU` — an app installed "for me only" would have stayed invisible, with the table acting as an old answer. The suite case demands it: the launcher comes out as `utente` (`HKCU`), not `macchina`.
* **Added**: **startup** takes the same path: the executable to launch is the one registered by the system, no longer the name derived from the CLI with a string substitution. They were two copies of the same information.
* **Fix**: `craft-bridge-recon.py` no longer builds paths by hand either (`<root>\<Name>`): it asks the shim for the folder registered by the system, and `--root` remains the fallback for unregistered apps. Same function, same source: all 12 apps including PdfCraft resolve from the registry.
* **Added**: `doctor` has a ninth check, `posizione app`: it says whether the path comes from the registry, and when system and table diverge it **shows it** (the system wins) instead of staying silent.
* **Added**: new node `docs/architecture/app-locations.md` (who knows what, the rule of the three outcomes, why startup does not go through the launcher).
* **Measurement**: 11/11 paths from the `App Paths` registry, with the table confirming; startup verified live (GridCraft: pid 10040 on `C:\Program Files\GridCraft\gridcraft.exe`, handshake `peer=craft`, `modalita' bridged`, 21 tools, app line `control channel listening on 127.0.0.1:7975`). Suite at 16 cases, 12 in `--static` mode; OKF bundle at 31 concepts and 139 relations (the counts before the four cases on the translator above).
* **Measurement**: the ArtCraft launcher offers no way to start or install an app from the command line — in the executable the only argument is `--hidden`, there is no `--install`/`--launch`, and no URL scheme is registered under `Classes`; upstream issues #128 and #148 ask for exactly this. Its local state is the window (`app.ron`) plus the release catalogue cache (`feed.json`, `releases.json`): it does not keep a list of what is installed and where. The apps are per-machine MSI packages (`MsiExec.exe /X{GUID}`), so their installer registers the path. Hence the choice: startup stays with the app, and the launcher contributes the other half of the question (which release exists), which is the one `craft-bridge-feed.py` uses.
* **Added**: `craft-bridge-feed.py --bytes` compares the installed `<slug>-cli.exe` with the file of the same name inside the published package, read in memory without extracting anything: it is the only answer that says "this is the release" instead of "it claims to be it". Three questions in a row (published archive? installed CLI? identical file?) and each one can stop the others.
* **Added**: `--download <slug>` downloads a package on explicit request, one app at a time, `https` only and only from the feed hosts; the feed digest is verified **before** the file is used (it stays `.parte` and is deleted if it does not match). Cache in `~/.craft-bridge/releases`, which is not the launcher's folder.
* **Measurement**: the installed SoundCraft `soundcraft-cli.exe` and the member inside the portable package have the same sha256 (`915ee3abb121b7b9...`); the downloaded archive matches the published digest (`cd5f8d98257f7711...`), 14.3 MB in 2 s. Negative test: one extra byte in the cached archive → `FIX byte ... non e' quello pubblicato`, exit 1. Of the 11 apps only SoundCraft has the archive on disk: the others are a `nota` with the command to fetch it.
* **Added**: a unit case on the bytes (fake archives: identical, different, tampered archive, missing CLI, missing member, preference for the CLI-only archive) and the download rules in the safety rules. Suite at 14 cases, 10 in `--static` mode.
* **Added**: `craft-bridge-feed.py` reads the ArtCraft launcher feed (source repo, latest release, packages with their sha256) and compares it with the installed build: the version of an executable says what it claims to be, not whether it is the published release. `--downloads` compares the bytes of the already downloaded packages with the published sha256, the only case that accuses anything; a missing launcher stays a declared gap.
